# v0.1.0 里程碑计划

> 状态：规划（2026-10-11 立项）。本文档是版本键控的路线图：维护分期、架构决策与风险状态；
> 不是变更日志——进度以 OpenSpec change 归档与 git 提交为准。大方向变更时同步更新本文档。

## 1. 里程碑目标与范围

v0.1.0 定位为**首个可运营版本**：多用户可用、生成可计费、运营可管理。四个功能需求：

| # | 需求 | 范围界定 |
| --- | --- | --- |
| 1 | 生产级 AI 画布 | 对话生成图片与海报（全链路已存在），补生产化运维面与积分闸门 |
| 2 | 灵活 Agent 扩展 | 开发者文件级 drop-in + 后台启停开关；自定义 Agent 可调用项目模型能力（装配层已有） |
| 3 | admin 后台管理系统 | **独立部署的管理端应用**：用户 / 邀请码 / 积分运营 / Agent 开关 / 模型配置 / 监控 + 审计 |
| 4 | AI 积分模块 | 预扣冻结 + 终态结算的积分账本；余额不足禁用画布生成功能；后台手动发放（无支付） |

明确不在 v0.1.0 范围：支付充值、终端用户 UI 创建自定义 Agent、多实例部署 / 分布式任务队列、Agent 市场。

## 2. 现有结构适配性分析

```
需求                        现状                          缺口
------------------------------------------------------------------------------
1. 生产级 AI 画布          ████████░░ ~80% 已存在        生产化运维面 + 积分闸门
2. Agent 扩展模块          █████████░ ~85% 已存在        后台启停开关、save_asset 工具
3. admin 后台管理系统      ░░░░░░░░░░ 0%                 全新：权限 + 独立应用 + 配置 DB 化
4. AI 积分模块             ░░░░░░░░░░ 0%                 全新：账本 + 定价 + 闸门
```

**需求 1（画布）**——全链路已在：全屏画布 + 悬浮聊天面板、SSE 流式、混合生成
（文生图 + HTML→Playwright 海报截图）、任务执行器（进程内，并发 2 / 超时 90s / 持久化 /
重启清理）、失败卡重试、会话记忆 compact、血缘引用（referenceAssetId）、i18n / 明暗主题。
缺口：请求 ID 日志等可观测性、错误面完整性、积分闸门接入。

**需求 2（Agent 扩展）**——架构已就位：`AgentDefinition` 声明式定义文件级 drop-in 注册
（零运行时改动）、ToolRegistry 按名授权（越权工具被拦截）、`models.main.capabilities`
能力声明 + 装配层 fail-fast（poster-designer 已示范 vision 声明）。缺口：后台启停开关、
`save_asset` 工具补全。

**需求 3（admin）**——零基础。`users` 表无 role 列；配置全部在 env（`src/lib/config.ts`）
+ 代码内 catalog（`TEXT_PROVIDERS` / `IMAGE_PROVIDERS`）；可管理素材仅 `invite_codes` 表
与 `users.status`。工作量本质是两件事：① 权限模型（role 列 + requireAdmin）；
② 配置从 env / 代码迁到 DB overlay（"统一管理"意味着运行时可改，env 只做默认值）。

**需求 4（积分）**——零基础。核心难点在扣费与任务生命周期的一致性（生图 10–30s，
不能成功后扣）：

```
用户发起生成
  | (1) 闸门：余额 >= 预估成本？ 否 --> 402，前端禁用生成入口
  v
创建任务 --> 预扣（冻结 frozen）
  |
  +- succeeded --> 结算：冻结 --> 实扣（按实际成本，多退少补）
  +- failed / canceled --> 释放冻结
  +- 服务重启标记 failed（executor 现有逻辑）--> 也必须释放冻结  <-- 最易漏点
```

闸门覆盖面是隐藏工作量大头：`/api/chat` 主入口、画布失败卡重试、设计页导出、未来批量——
所有生成入口必须收敛为 domain 层统一闸门服务，禁止各 route 自查。

## 3. 架构决策记录

| # | 决策点 | 结论 | 放弃的备选与理由 |
| --- | --- | --- | --- |
| D1 | 仓库形态 | **pnpm workspace monorepo**：`apps/web` + `apps/admin` + `packages/{config,db,auth,llm,domain}` | 方案 A（同应用 admin 路由组）：省 2–3d 但无法满足独立部署 / 独立发布；完整 DDD 仪式（聚合根 / 领域事件 / CQRS）：单一限界上下文 + 单部署 + 小团队，收益低摩擦大 |
| D2 | admin 登录态 | **共享登录态**：同一 HMAC session cookie（生产 domain 设父域；dev localhost 跨端口天然互通）；`requireAdmin` = 完整验签 + 过期 + `status=active` + 会话版本 `tv` 一致 + `role=admin` | 独立登录体系：多 +1–2d 且运营记两套账号，v0.1.0 无必要 |
| D3 | 积分扣费语义 | **预扣冻结 + 终态结算**：账本含 `frozen` 态；全终态（成功 / 失败 / 取消 / 重启清理）都有对应结算路径；DB 条件 UPDATE 保证原子性 | 成功后扣：生图成本高，负余额风险不可接受 |
| D4 | 自定义 Agent | **开发者 drop-in + 后台启停开关**；终端用户 UI 创建推 v0.2 | 用户 UI 创建：需 DB 存储 + 提示词 / 工具授权编辑界面，范围大数倍 |
| D5 | 积分发放 | **后台手动发放 / 扣减**（无支付）；全操作落审计日志（`admin_audit_log`，v0.1.0 就带——事后补历史极难） | 接入支付：v0.1.0 不做 |
| D6 | 部署形态 | **web 单实例**（executor 不 worker 化）；admin 独立部署（本身就是第二应用）；积分用纯 DB 事务，天然兼容未来多实例 | 多实例 + BullMQ：v0.2 扩容期再做，架构文档已预留 Service 接口不变 |
| D7 | 架构模式 | **延续 DDD-lite**：domain（实体 + 领域逻辑）/ db（仓储接口 + 实现）/ infra（技术实现）分层进 packages，边界从 ESLint 约定升级为编译期事实 | 教科书式完整 DDD：见 D1 |

**配置三层链**（admin 配置管理与多供应商演进的合并设计，v0.1.0 一次定调）：

```
生效配置 = DB overlay（admin 可改，运行时热读 + 短缓存）
         ?? env（部署默认值，现状不动）
         ?? 代码目录（catalog 常量，最终兜底）
```

双读过渡期语义：**DB 有值即赢**，写入 spec 后 seed 即视为迁移完成。定价、Agent 开关、
模型目录启停 / 角色默认模型都走这条链；供应商密钥永远只在 env，不入库。

## 4. 目标 workspace 结构

```
oops/（pnpm workspace）
├── apps/
│   ├── web/          # 现有应用整体迁入（app/components/lib/i18n + server 的 infra/agent）
│   └── admin/        # 后台管理系统（新 Next.js 应用，独立部署）
├── packages/
│   ├── config/       # @oops/config   env schema（双端共用）
│   ├── db/           # @oops/db       drizzle schema + client + repos（admin 硬依赖）
│   ├── auth/         # @oops/auth     password + session 验签 + requireUser/requireAdmin
│   ├── llm/          # @oops/llm      catalog + resolver（admin 模型配置页消费）
│   └── domain/       # @oops/domain   credits / tasks（M1 随积分域抽出）
├── pnpm-workspace.yaml
└── ...
```

**留在 `apps/web` 不抽的**：agent 运行时（registry / runtime / tools / definitions）、
infra（storage / render / providers）、全部 UI——admin 用不到它们。后台管 Agent 开关走
配置表的 agent id 键值（web 端运行时按 id 解析开关），不需要 import agent 代码。

## 5. 分期计划

### M0 架构基座（~4–5d）

- M0.1 workspace 化：现有代码迁入 `apps/web`，tsconfig paths / ESLint / vitest / CI 双端编排
- M0.2 抽包 `@oops/config`、`@oops/db`、`@oops/auth`、`@oops/llm`；`users.role` 迁移
  （默认 `user`）+ `requireAdmin`；web 端 `requireUser` 行为零变化
- M0.3 `apps/admin` 脚手架：Next.js 空壳 + 共享 cookie 验签门卫 + 管理布局骨架

验收：双端 `pnpm lint && pnpm typecheck && pnpm test` 三绿；web 全功能冒烟零回归；
web 登录后在 admin 免登录进入空管理页，非 admin 角色 403。

### M1 积分域（~4–5d）

- M1.1 抽 `@oops/domain`（tasks 迁入）；credits 域：`credit_ledger` 表 +
  `users.credit_balance` 物化列 + 定价表（seed 初始数据，后台可改为 M2.3 交付）
- M1.2 预扣 / 结算状态机接入 task-executor 全终态（成功实扣退差 / 失败 / 取消 / 重启清理释放）
- M1.3 web 端闸门：domain 单点闸门服务，`/api/chat` 与任务创建入口统一接入；402 结构化响应
- M1.4 前端：余额展示 + 402 → 生成入口禁用态

验收：全终态对账单测（含重启释放冻结路径）；并发扣费原子性测试（条件 UPDATE）；闸门
入口清单测试；i18n 词典同步（zh / en）。

### M2 后台管理系统（~5–6d）

- M2.1 用户管理（搜索 / 列表 / 启停）+ 邀请码管理（单个 / 批量生成 / 作废 / 用量）
- M2.2 积分运营：发放 / 扣减 / 流水查询 / 对账视图 + 定价编辑
- M2.3 Agent 启停开关 + 模型配置页（目录启停 / 定价 / 角色默认模型）→ 接配置三层链
- M2.4 运营监控看板（tasks 只读：状态 / 失败率 / 耗时）+ `admin_audit_log` 审计（全操作）

验收：所有 admin route 过 `requireAdmin`；所有写操作落审计（who / what / when / 前后值）；
i18n 同步。

### M3 Agent 增强（~2–3d）

- M3.1 `save_asset` 工具补全
- M3.2 Agent 开关消费：web 端 AgentRegistry 按 DB 开关过滤下线 Agent（`/api/agents` 与
  会话内均生效）
- M3.3（可选）`schedule_batch` 批量出图

### M4 画布生产化（~2–3d，独立轨，可与 M1 / M2 并行）

- M4.1 请求 ID 日志 + 服务端错误结构化收尾
- M4.2 错误面完整性（画布失败卡 / 聊天侧错误文案覆盖全路径）
- 明确不做：BullMQ worker 化（v0.2）

## 6. 依赖关系与关键路径

```
M0 架构基座 ──────► M1 积分域 ──────► M2 后台系统 ──────► M3 Agent 增强
 users.role          @oops/domain        用户/邀请码          开关消费(M2.3)
 requireAdmin        账本+状态机          积分运营(M1)         save_asset
 admin 脚手架        闸门+402            配置 DB overlay
 │
 └──► M4 画布生产化（独立轨，无阻塞依赖）
```

关键路径 = M0 → M1 → M2（M2.2 积分运营硬依赖 M1 账本）。M1 是风险最集中区，
M0 完成后立即启动；M4 可随时插队但建议排在 M1 之后（错误面会因积分闸门再动一轮）。

## 7. 风险清单与缓解

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | 冻结泄漏（重启 / 崩溃后冻结不释放） | 用户积分被吞，对账灾难 | executor 重启清理路径必须触发释放；全终态对账单测进门槛 |
| 2 | workspace 迁移破坏面（import paths / Turbopack / vitest / CI） | 迁移期开发停摆 | 独立 PR、迁移与功能不混做；双端三绿 + web 全功能冒烟后才继续 |
| 3 | 闸门漏覆盖（多入口分散自查） | 漏扣费 | 闸门收敛 domain 单点服务；生成入口清单测试 |
| 4 | env → DB 配置双读语义不清 | 配置行为不可预测 | "DB 有值即赢"写进 spec；seed 即迁移完成 |
| 5 | admin 范围膨胀成低代码平台 | 排期失控 | 收敛为六张管理面（用户 / 邀请码 / 积分 / Agent 开关 / 模型配置 / 监控+审计），其余拒绝 |
| 6 | 共享 cookie 域配置错误 | admin 登录态不通 | dev 端口互通先验证；生产父域部署写进部署清单 |
| 7 | 单实例假设失效（增长快于预期） | 重复执行任务 | 积分已兼容多实例；仅 executor 需 worker 化（v0.2 预案），触发条件记录在案 |

## 9. v0.2 演进预告

- **多实例 + BullMQ**：task executor 换 Redis 分布式队列（Service 接口不变）
- **用户 UI 自定义 Agent**：DB 存储 Agent 定义 + 提示词 / 工具授权编辑界面（Agent 市场前置）
- **支付充值**：接入支付渠道，积分发放自动化
- **Agent 市场 / 局部重绘抠图**：新工具加入 ToolRegistry
